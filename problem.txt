# 運用ルール:
# - 開発中に見つかった問題(想定した動きをしない、デザイン崩れ等)や修正要望は全てここに記録する
# - 修正プロセス(CLAUDE.md「問題修正プロセス」参照・省略禁止):
#   問題共有 → problem.txtに記録 → 原因を徹底調査 → 原因特定 →
#   タスクを切り出しprogress.txt/manual-work.txtに追加 → 修正作業 → 解決済みに更新

# - 原因調査・特定・切り出しタスクの欄を埋めずに修正作業を開始してはならない
# - テストデータの変更等で問題を回避しただけの場合は「解決済み」にしない

## P-001: npm audit で依存パッケージの脆弱性警告(high 46 / moderate 15)
- 記録日: 2026-10-07
- 状態: 解決済み(リスク受け入れ。リリース前に再確認)
- 発生箇所: Phase 1-1(Expo 初期化時の依存パッケージ)
- 問題内容:
  想定した動き: 依存パッケージに既知の脆弱性がない、またはリスクを評価済みである
  実際の動き: `npm audit --omit=dev` で 61件(15 moderate, 46 high)。@expo/config-plugins / @expo/config /
              @expo/prebuild-config / @expo/inline-modules など Expo のビルド用ツール経由のもの
- 再現手順:
  1. `npm ci`
  2. `npm audit --omit=dev`
- 原因調査(2026-10-07 メインエージェント):
  npm audit の元になっている advisory は5件。それぞれの経路を npm ls で追った。
  - braces(high, DoS): expo → @expo/metro → metro-file-map → micromatch。開発・ビルド時のみ
  - node-forge(high, 署名検証): expo → @expo/cli(@expo/code-signing-certificates)。開発・ビルド時の CLI のみ
  - uuid(moderate): expo → @expo/config-plugins → xcode。prebuild 時のみ
  - sprintf-js(moderate, DoS): react-native → @react-native/jest-preset → babel-jest → … js-yaml。テスト時のみ
  - decode-uri-component(moderate, DoS): expo-router → query-string。アプリのバンドルに含まれる。
    不正な % エンコードの URL(ディープリンク)を受け取ると処理が重くなる可能性がある。影響は利用者の端末上のアプリだけで、データ漏えいはない
  残りの61件は、上の5件に依存している Expo 系パッケージの数え上げ。
  `npx expo install --check` の結果は「Dependencies are up to date」(Expo SDK 57 の推奨どおり)。
  `npm audit fix --force` は Expo の推奨版から外れる破壊的変更になるため、使わない
- 特定した原因:
  Expo SDK 57 が依存しているツール群の推移的依存。プロジェクト側では、Expo の推奨版を保ったままでは修正できない
- 対応方針(2026-10-07 ユーザー承認):
  - 開発・ビルド時のみのもの(4件)は、リスクを受け入れる
  - decode-uri-component は影響が小さいので現時点では受け入れ、Phase 8 のリリース前に Expo の更新で解消されたかを再確認する
- 切り出したタスク:
  progress.txt 8-5(リリース前の依存脆弱性の再確認)
- 解決日: 2026-10-07
- 解決内容:
  ユーザー承認のうえでリスクを受け入れた。リリース前に 8-5 で再確認する
- 追記(2026-10-07): 1-4 で @bacons/apple-targets(package.json の dependencies に入っているが、使うのは prebuild 時のみ。アプリのバンドルには含まれない)を追加した。
  これに含まれる @expo/config-plugins → xcode → uuid 系により、`npm audit --omit=dev` が 61 → 65件(moderate 15→17、high 46→48)になった。
  同じ系統(ビルドツール由来)なので、この方針の範囲として受け入れる。8-5 で再確認する

## P-004: shared/ の lint ルールで shared/ の外への相対 import を検出できない
- 記録日: 2026-10-07
- 状態: 解決済み
- 発生箇所: Phase 2-1(eslint.config.js の shared/ 用 no-restricted-imports)
- 問題内容:
  想定した動き: shared/ からは shared/ 内の相対 import 以外を import するとエラーになる(アプリ・Functions 両方で動く純粋なコードを保つため)
  実際の動き: `import x from '../src/app/index'` のように shared/ の外を指す相対 import がエラーにならない
- 再現手順:
  1. shared/x.ts に `import x from '../src/app/index';` と書く
  2. `npx eslint shared/x.ts` → 終了コード 0
- 原因調査:
  2-1 のレビューで発見。eslint.config.js の該当ルールを確認した。
  パターンは regex `^(?!\.{1,2}/)` で、「./ か ../ で始まらないもの」だけを禁止している。
  そのため ../ で始まるパスは、どこを指していても許可される。
- 特定した原因:
  正規表現がパスの開始文字だけを見ており、解決後の場所が shared/ 内かを判定していない
- 切り出したタスク:
  progress.txt 2-1b
- 解決日: 2026-10-07
- 解決内容:
  import 元ファイルの位置から解決先を判定するローカルルール gokaku/shared-imports-only に置き換えた。
  tests/lint(27件)で恒久的に検証している。ルールを無効化すると、エラーを期待する19件が失敗することを確認済み(2-1b レビューPASS)

- 再現手順:

- 原因調査:
  2-1c の実装担当の報告をきっかけに、メインエージェントが package.json を確認した(lint = "expo lint")。
  `npx eslint .` も実行し、上の失敗を再現した。

  検査範囲が shared/・functions/src・tests/・src/・設定ファイルであることを確認した(2-1d レビューPASS)
